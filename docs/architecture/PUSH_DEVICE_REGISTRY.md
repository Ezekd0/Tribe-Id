# Owned push-device registration (T36)

The existing native app uses Expo. The initial server registry explicitly accepts Expo Push Service tokens and Android/iOS platform metadata; it does not accept raw APNs/FCM tokens or browser subscriptions. This is an integration choice consistent with the existing app, not proof of provider configuration or permission. Expo documents `getExpoPushTokenAsync` and the push-service routing flow; its server SDK recognizes wrapped Expo/Exponent tokens and UUID-form tokens. The API adds a 256-character bound and rejects whitespace/control characters. See [Expo delivery documentation](https://docs.expo.dev/push-notifications/sending-notifications/) and the [official server SDK token predicate](https://github.com/expo/expo-server-sdk-node/blob/main/src/ExpoClient.ts).

| Method | Path | Body | Result |
| --- | --- | --- | --- |
| PUT | `/api/v1/me/push-device` | `{provider:'expo',platform:'android'|'ios',token:string}` | Empty 204 |
| DELETE | `/api/v1/me/push-device` | None | Empty 204 |

Bearer authentication determines both user and current device session. No client-supplied user/session/Tribe/registration ID is accepted. Strict prevalidation rejects unknown query/body fields, wrong types and unsupported token/platform formats. Registration revalidates the enabled, email-verified account, current credential version, session expiry/revocation and existing mandatory privileged MFA rule inside a user-then-session transaction. Registration does not enable push preferences; explicit informational opt-in remains separate.

Migration011 stores one registration per session and caps active registrations at 100 per account, consistent with the existing bounded device-management surface. Routing tokens are AES-GCM encrypted with a session-bound context. A separate HKDF-derived HMAC key provides opaque global token deduplication; raw tokens and unhashed token fingerprints are not persisted, returned or audited. The encryption key comes from configured server secrets. Key rotation must preserve/re-encrypt existing routing material and rebuild deduplication indexes through an authorized operation; silent key rotation compatibility is not claimed.

Repeating an unchanged registration is idempotent. Replacing the token updates the current session only. A token may move between the same user's sessions. A token belonging to a different live session/account yields a generic conflict without owner identifiers; it can be reused after the prior session is revoked/expired. Possession of an Expo token is not independent proof of control over physical hardware. Client secure handling and real-provider/device qualification remain necessary.

DELETE affects only the caller's current session and is idempotent. Successful mutations and audits commit together; audit failure rolls back registration changes. Audit rows contain action, actor and request ID only. The existing credential redaction excludes request/response bodies and token fields; no registry path logs token material.

A database trigger removes routing registrations for every existing session-revocation update, covering logout, device revoke, logout-all, replay/reset and other revocation paths. Session expiry cleanup cascades registrations. Delivery also rechecks current session/account/credential/MFA/membership validity before resolving targets, so stale routing rows cannot bypass revocation. Push with no eligible registered device is suppressed. Generic notification/Tribe IDs remain the only content payload; decrypted routing tokens exist transiently only as adapter destinations, never in the persisted delivery payload or logs. A revocation during an already in-flight external send cannot retract that submission.

T37 adapters must map each device submission/receipt independently, retain submitted-versus-delivered distinction, and fence stale receipt invalidation against token rotation. The current generic queue has no production Expo client, provider credentials, scheduler, APNs/FCM qualification or receipt implementation. T38 still requires native permission/token acquisition, registration after login/rotation, unregister/logout behavior, token refresh and authenticated navigation on signed Android/iOS devices.

Verification sources: `apps/api/src/modules/push-device.test.ts` validates strict inputs and non-echoing owned routes. `scripts/verify-push-devices.ts` requires a disposable PostgreSQL database and exercises HMAC/encryption, deduplication/rebinding, foreign conflict, current-only deletion, concurrent registration, atomic audit rollback, actual logout-trigger removal and stale-account/session delivery suppression. All push transports in tests are local injected stubs; no provider traffic or device delivery is claimed. T36 remains partial until native/provider qualification is completed.
