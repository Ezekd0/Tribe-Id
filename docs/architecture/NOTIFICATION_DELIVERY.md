# Informational notification production and durable delivery

T20 produces inbox rows and encrypted delivery jobs in the same transaction as the domain mutation/audit. Mandatory authentication/security mail remains in the separate existing `auth_outbox`; informational opt-outs do not affect it.

| Actual domain change | Eligible audience |
| --- | --- |
| Announcement publication | All active Tribe memberships with enabled, email-verified accounts |
| Event publication | Same all-active audience |
| Published event edit or event cancellation | Active eligible memberships currently registered or attended |
| Own event registration/cancellation | Acting active eligible membership only |

Draft edits, announcement edits, repeated publication, unchanged event edits, repeated registration/cancellation and repeated event cancellation do not produce duplicate informational events. Event cancellation and own registration cancellation have distinct inbox wording. Inbox title is the relevant announcement/event title; body is a short fixed explanation. Optional source metadata identifies the resource. Cancellation wording communicates the outcome without requiring access to an upcoming-event detail page.

`NotificationPublisher.publish` requires the domain transaction's client. A unique event UUID deduplicates replay; conflicting reuse of an event ID is rejected. Database uniqueness covers recipient/event inbox rows and notification/channel jobs. Fanout uses tenant-scoped set selection and bulk inserts. Recipient memberships use stable primary keys; domain authority membership locks use `FOR NO KEY UPDATE` to retain role/status safety while permitting notification FK key-share locks. Source event, inbox, encrypted jobs and mutation audit all roll back with a failed mutation.

Every eligible recipient gets an inbox entry. Email jobs require both the informational-email flag and explicit consent timestamp; push jobs require the push flag. Defaults remain opt-out. If opted-in jobs are required without an encryption key, publication fails with 503 and rolls back instead of dropping delivery. The app composition injects an explicit configured key. Ciphertext uses a distinct AES-GCM context and contains only notification/Tribe IDs. No destination email, device token, announcement body, event details, name or title is stored in the delivery payload.

## Worker contract

`NotificationDeliveryWorker` has no default provider and sends no traffic by itself. Callers explicitly inject channel transports. Unsupported channels remain pending. A run processes at most 50 jobs, each claimed immediately before its send. PostgreSQL `SKIP LOCKED` claims use a 60-second lease and opaque fencing token. Attempts are bounded at eight; retries use capped exponential delay. A reclaimed lease invalidates the previous worker's finalization. Terminal failures erase ciphertext and persist only a bounded error class; arbitrary provider error text is discarded.

The worker rechecks active membership, enabled/verified account, current channel consent and resource scope/status immediately before sending. Email resolves the current verified address at attempt time. It suppresses withdrawn consent and unavailable recipients/resources. These checks cannot retract mail or push already handed to a transport; consent changes during an in-flight request affect later attempts. No user/membership database locks are held across external calls. Adapters must respect the supplied abort signal and bounded timeout.

An injected adapter receives an opaque job idempotency key, destination membership (current email only for email), fixed generic title/body, and notification/Tribe IDs for authenticated inbox navigation. Push must never expose private content on lock screens. A transport outcome can be `delivered`, `failed`, or `submitted` with a bounded opaque reference. Provider acceptance/ticket submission is not proof of delivery. Submitted jobs remain separate awaiting future receipt qualification. Successful/submitted/suppressed/failed jobs erase encrypted payloads. Do not log envelopes, destination addresses, tokens or raw provider errors.

Delivery is at least once: a crash after transport acceptance and before local acknowledgement can duplicate a notification unless the provider honors the job idempotency key. A timed-out adapter that ignores cancellation can also complete later. Exactly-once delivery is not claimed.

## Evidence and remaining scope

`scripts/verify-notification-delivery.ts` requires a disposable PostgreSQL database and injects local in-memory transports only. It checks atomic producer/audience rules, concurrent broadcasts, event/recipient idempotency, rollback on missing encryption configuration/inbox failure, generic encrypted payloads, consent suppression, current membership eligibility, retry exhaustion, lease reclaim/fencing and concurrent claims. Push acceptance is tested as submitted, not delivered; missing push adapter leaves pending jobs.

T36 provides authenticated device registration; native permission/token handling is tracked separately. T37 now provides locally verified provider adapters and a runnable one-shot worker below. Scheduler/deployment and real-provider/device acceptance remain release gates. Informational job retention/cleanup and operational alert thresholds require the associated operations qualification; no arbitrary data-retention deletion policy is introduced here. Inbox APIs/native navigation remain separately owned. Inbox-only or local-transport evidence does not satisfy the required push launch scope.

## T37 local Expo provider implementation (2026-10-24)

Expo matches the existing Expo-native token registry. `ExpoProvider` uses fixed HTTPS Expo endpoints, explicit enhanced-security access token, disabled redirects, bounded 128 KiB streamed JSON responses, bounded batch sizes and caller cancellation. No endpoint or TLS override exists. Tests inject a local fetch function; they do not contact Expo. The adapter always replaces copy with “You have a Tribe notification”; only opaque notification and Tribe IDs appear in routing data. Provider text/errors and device tokens are never logged or retained in attempt records.

Migration 012 adds a device-level ledger, unique per parent job/device. States are queued, attempted, provider accepted, provider rejected, retry scheduled, permanently failed, provider handoff, receipt unknown and suppressed. Tokens remain encrypted exclusively in the registry; attempts store its keyed fingerprint so an old invalid-token response cannot revoke a replacement token. Sending rechecks the registry generation against the token snapshot. Already accepted devices are skipped when another device retries. Device leases and parent leases fence concurrent workers; eight attempts bound retries. Parent terminal status can be failed if every device failed. A crash/network timeout after remote acceptance and before durable ticket storage remains ambiguous and can cause a duplicate; Expo does not provide exactly-once idempotency. This limitation is explicit.

Receipt polling starts after 15 minutes and repeats at 15-minute intervals. Success becomes **provider handoff**, never confirmed device delivery. Missing receipts are not grounds for resending accepted pushes; after 23 hours they become receipt unknown. A definitive MessageRateExceeded negative receipt schedules the corresponding device and parent again when attempt budgets permit. Permanent errors stop retry; DeviceNotRegistered removes only the matching token generation. Receipt processing is leased and idempotent. Generic provider failures are classified without persisting arbitrary text. Bounded aggregate state counts are emitted by the worker; operational alert thresholds remain staging qualification work.

One-shot compiled entry point: `node apps/api/dist/operations/push-worker.js`, with explicit `PUSH_DELIVERY_ENABLED=true`, `DATABASE_URL`, `AUTH_ENCRYPTION_KEY` and secret `EXPO_ACCESS_TOKEN`. Set up Expo enhanced push security with that access token before external qualification. This worker processes at most 50 parent jobs then 50 receipts and exits; run on an approved scheduler with concurrency bounds and prevent overlapping scheduler growth. Email jobs remain pending unless explicitly enabled; mandatory SMTP authentication mail remains separate. Starting the API or running checks never enables push delivery. No real provider calls, credentials, paid resources or deployment were used for local evidence.

References: [Expo sending and receipt semantics](https://docs.expo.dev/push-notifications/sending-notifications/). Expo recommends exponential backoff, checking receipts after 15 minutes, and stopping sends to DeviceNotRegistered tokens; receipts are removed after 24 hours. Its successful receipt acknowledges FCM/APNs handoff, not delivery to a person. Production still requires project credentials, signed native builds, approved provider access, real-provider receipt qualification and physical-device acceptance.

### Opt-in informational SMTP adapter

`INFORMATIONAL_EMAIL_ENABLED=true` enables generic plaintext informational mail in the same one-shot worker, independently of `PUSH_DELIVERY_ENABLED`. It uses existing `readEnvironment`-validated AUTH/SMTP settings (`AUTH_ENABLED=true`, `SMTP_URL`, `MAIL_FROM`, authentication keys); production TLS and certificate validation remain enforced. Local-capture SMTP is limited to credential-free loopback and prohibited in production. Nodemailer connection, greeting and socket timeouts are bounded; URL/file content access is disabled. Each send has its own transport closed on abort or completion. The outer delivery worker rechecks informational-email consent and current verified address immediately before send. Security mail remains separate and cannot be opted out here.

Only fixed generic copy is mailed, with no notification resource IDs or titles. A deterministic job-derived Message-ID helps mail systems recognize repeat submissions; it cannot guarantee deduplication after ambiguous SMTP acceptance. Nodemailer must acknowledge the exact recipient. The job becomes submitted, never delivered; bounce/DSN and mailbox delivery confirmation are not implemented or claimed. Unit injection and a real loopback synthetic SMTP sink verify this behavior without external messages. Official references: [Nodemailer SMTP/TLS controls](https://nodemailer.com/smtp), [Message-ID and message fields](https://nodemailer.com/message).
